# 1 Purpose

PuzzleDSL is never rendered directly.

PuzzleDSL is first compiled into an intermediate representation called the Puzzle Render Tree (PRT).

The renderer only understands the PRT.

The renderer never reads PuzzleDSL directly.

---

# 2 Compiler Pipeline

Every question follows the exact same compilation pipeline.

PuzzleDSL

↓

Parser

↓

Abstract Syntax Tree (AST)

↓

Semantic Validator

↓

Constraint Validator

↓

Reference Resolver

↓

State Generator

↓

Puzzle Render Tree (PRT)

↓

Renderer

Every implementation SHALL follow this order.

---

# 3 Why an AST Exists

The AST separates

Authoring

from

Rendering.

LLMs author PuzzleDSL.

The renderer consumes the PRT.

Neither depends upon the other.

---

# 4 Compiler Responsibilities

The compiler SHALL

✓ Parse PuzzleDSL

✓ Validate schema

✓ Validate grammar

✓ Resolve references

✓ Resolve definitions

✓ Apply rules

✓ Generate timeline

✓ Produce render tree

The compiler SHALL NOT

✗ Guess data

✗ Modify logic

✗ Invent entities

✗ Repair broken questions

---

# 20 Renderer Contract

The renderer assumes

Every object valid

Every reference resolved

Every rule executed

Every frame generated

Renderer never checks correctness.

---

# 21 Compiler Determinism

Given identical PuzzleDSL

Compiler output SHALL always be identical.

Compiler randomness is forbidden.

---

# 22 Acceptance Tests

Compiler accepted only if

✓ Same DSL always produces same PRT

✓ No renderer logic exists

✓ No semantic logic exists inside renderer

✓ Invalid PuzzleDSL rejected

✓ Timeline generated automatically

✓ References resolved

✓ Constraints validated

✓ PRT independent of browser

✓ PRT independent of frontend framework

If every condition is TRUE

Compiler Version 1 accepted.
