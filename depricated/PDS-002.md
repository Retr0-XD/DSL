# 1. Purpose

This document formally defines PuzzleDSL.

PuzzleDSL is a Domain Specific Language designed for describing visual reasoning questions.

PuzzleDSL is NOT

• HTML

• SVG

• Canvas

• CSS

• React

• JSON

JSON is only the storage format.

PuzzleDSL is the semantic language.

---

# 2. Design Philosophy

PuzzleDSL represents meaning.

It never represents pixels.

Wrong

Rectangle

x=251

y=103

width=28

height=29

Correct

Square

Row 2

Column 4

Blue

Rotated 90°

The renderer decides where pixels go.

---

# 3. Language Model

PuzzleDSL is composed of only six concepts.

ENTITY

STATE

RULE

SEQUENCE

QUESTION

ANSWER

Everything else is derived.

If something cannot be expressed using these concepts, the language should evolve—not the renderer.

# 4. Language Hierarchy

Puzzle

│

├── Metadata

├── Entities

├── Rules

├── Timeline

├── Interaction

# 5. Core Objects

PuzzleDSL contains only seven object categories.

ENTITY

RULE

ACTION

STATE

TRANSITION

CONSTRAINT

PROPERTY

Every object in the language belongs to one of these categories.

---

# 6. ENTITY

Definition

A logical object that exists inside a puzzle.

Examples

Square

Circle

Triangle

Arrow

Digit

Letter

Grid

Cell

Operator

Entity has identity.

Two identical squares are still different entities.

Example

Square A

Square B

because each has a unique ID.

A property describes an entity.

# 8. STATE

A state represents every property of every entity at a specific moment.

Example

Frame 1

Square

Blue

Top Left

Rotation 0°

Frame 2

Square

Blue

Top Right

Rotation 90°

---

# 9. ACTION

An action changes one or more properties.

Examples

Move

Rotate

Mirror

Duplicate

Delete

Swap

Scale

ColorChange

Hide

Show

An action never exists without a target.

---

# 10. RULE

A rule defines WHEN an action happens.

Example

Every Frame

↓

Rotate 90°

Another

Every Second Frame

↓

Alternate Color

Rules describe behaviour.

Actions describe change.

---

# 11. TRANSITION

A transition converts one state into another.

State A

↓

Transition

↓

State B

Transitions never contain rendering information.

---

# 12. CONSTRAINT

A constraint limits behaviour.

Examples

Cannot overlap

Cannot leave grid

Must remain visible

Exactly one answer

Unique solution

Constraints are mandatory.

---

# 13. Primitive Philosophy

PuzzleDSL intentionally contains very few primitives.

Primitive Count should remain below 50.

If new questions require dozens of new primitives, the language has failed.

Priority

↓

---

# 22. Determinism

PuzzleDSL contains no randomness.

Forbidden

Random()

Shuffle()

Probability()

Random Color

Random Position

Questions must always render identically.

---

# 23. Immutability

Official question definitions are immutable.

Generation creates a new question.

It never edits an existing one.

Git manages version history.

The DSL does not.

---

---

# 30. Acceptance Criteria

PuzzleDSL is considered complete only if

✓ Every official dMAT puzzle can be represented.

✓ No rendering instruction exists inside the language.

✓ No browser-specific information exists.

✓ No framework-specific information exists.

✓ No entity depends upon pixels.

✓ Every entity has identity.

✓ Every transition is deterministic.

✓ Every rule is reproducible.

✓ Every question serializes to valid JSON.

If every condition is TRUE,

PuzzleDSL Version 1 is accepted.
