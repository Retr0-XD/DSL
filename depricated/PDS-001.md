# 2. Problem Statement

Modern Large Language Models (LLMs) are capable of generating high quality text but perform poorly when creating structured visual reasoning questions.

The primary causes are:

• Poor spatial reasoning
• Unreliable image generation
• Lack of deterministic layouts
• Inability to precisely describe diagrams
• Weak vision capabilities in free-tier models

This makes visual aptitude tests such as dMAT difficult to reproduce.

The problem is NOT that LLMs cannot reason.

The problem is that there is no deterministic language capable of representing these questions.

---

# 3. Objective

Create a Domain Specific Language (DSL) capable of representing every supported dMAT question using structured data instead of images.

The language must satisfy five properties.

1. Human Readable
2. Machine Readable
3. Machine Writable
4. Deterministic
5. Extensible

Every supported question must be expressible without manually drawing graphics.

# 5. Scope

Version 1 supports ONLY the following question families.

• Figure Sequence
• Latin Squares
• Mathematical Equations
• Subject Module

No other aptitude question type shall be implemented during Version 1.

---

❌ OCR

❌ Image Recognition

❌ Image Generation

❌ AI Drawing

❌ GUI Editors

❌ Drag-and-drop puzzle builders

❌ Visual authoring

❌ Multiplayer

❌ Accounts

❌ Online collaboration

❌ Leaderboards

❌ Timed exams

❌ Mobile application

If a feature does not improve question representation, rendering or generation, it does not belong in Version 1.

# 8. Core Design Principles

PuzzleDSL follows ten principles.

## Principle 1

Semantics before visuals.

Every visual element must exist because of semantic meaning.

Never the opposite.

---

## Principle 2

Rendering is deterministic.

The same JSON shall always produce identical output.

Random rendering is forbidden.

---

## Principle 3

The renderer is stateless.

Rendering one question shall never affect another.

---

## Principle 4

The renderer does not reason.

It only displays.

---

## Principle 5

The DSL is implementation independent.

The language shall not depend upon

HTML

SVG

Canvas

React

Vue

Angular

NextJS

or any frontend framework.

---

## Principle 6

Every visual object has purpose.

Decorative graphics are forbidden.

Everything rendered must contribute toward solving the puzzle.

---

## Principle 7

Questions are compositions.

Questions shall never exist as hardcoded templates.

Instead

Question

↓

Primitive

Primitive

Primitive

↓

Composition

---

## Principle 8

The language is finite.

The number of primitives should remain intentionally small.

New question types should emerge from combining primitives.

Not by creating hundreds of new primitives.

---

## Principle 9

Validation is mandatory.

Invalid questions must never be rendered.

---

## Principle 10

Backward compatibility.

Future DSL versions must continue supporting previously authored questions.

Breaking changes are forbidden.

---

# 9. Definitions

This specification uses the following terminology.

## Primitive

The smallest semantic operation that cannot be further divided.

Examples

Move

Rotate

Mirror

Count

Alternate

---

## Composition

A combination of primitives.

Example

Move

+

Rotate

+

Color Cycle

---

## Renderer

A deterministic system that converts Question JSON into a visual representation.

---

## Semantic Layer

The logical meaning of a question.

---

## Visual Layer

The graphical appearance of semantic objects.

---

## Interaction Layer

How the user interacts with the question.

---

## Question

A fully defined reasoning problem.

A question is never an image.

A question is structured data.

# 14. Acceptance Criteria

Version 1 SHALL be accepted only if all conditions are satisfied.

□ Every official puzzle recreated.

□ Every puzzle represented only through DSL.

□ No image generation.

□ No OCR dependency.

□ No GUI authoring dependency.

□ Text-only LLM successfully creates new questions.

□ Renderer produces deterministic layouts.

□ Schema validates every question.

□ Invalid questions rejected before rendering.

□ Entire project functions offline after installation.

---

# 15. Failure Conditions

The project SHALL be considered failed if any of the following occur.

• Renderer guesses missing data.

• LLM outputs HTML instead of DSL.

• Questions require images.

• Renderer performs reasoning.

• Multiple valid answers exist without explicit support.

• JSON cannot be understood without external documentation.

• New primitives are added to compensate for poor language design instead of extending existing compositions.
